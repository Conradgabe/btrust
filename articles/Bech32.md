# Bech32 as an Encoding/Error-Correction Scheme

SegWit modified what could go _inside_ a transaction output; Bech32 changed how you _represent_ that output as a human-shareable address.

## Why Bitcoin Needed a New Address Format (Base58's Weaknesses)

Bitcoin's legacy Base58 encoding format has two primary categories of weaknesses: technical/computational weaknesses and functional/protocol weaknesses.

### Technical & Computational Weaknesses

1. **High mathematical complexity:** Unlike Base64 or Base32, which align cleanly with base-2 bit shifts, Base58 is not a power of two. Converting binary data to Base58 therefore requires intensive, multi-precision large-integer division. This translates to a quadratic runtime (O(n²)) operation, slowing down processing speeds when a node must decode thousands of addresses per block.
2. **Case-sensitivity:** Base58 utilizes a mixed-case alphabet (both lowercase and uppercase letters), which makes it highly prone to human error compared to Base32. It's difficult to read aloud safely or enter manually on smaller smartphone keyboards.
3. **Suboptimal checksum guarantees:** Base58Check relies on a double SHA-256 hash checksum. While it successfully catches random typos, it offers no algebraic error-correction guarantees, it cannot determine _which_ character is wrong, nor does it protect efficiently against specific character-swapping patterns. Detection is trivial; correction is where the magic happens.
4. **QR code inefficiency:** Since it mixes uppercase and lowercase characters, QR code scanners cannot use the highly optimized alphanumeric mode. Instead they default to binary mode, producing larger, denser QR codes that are harder for low-resolution mobile cameras to scan quickly.

### Functional & Protocol Weaknesses

1. **Native SegWit not supported:** Base58 addresses do not natively support Segregated Witness (SegWit). Sending transactions to Base58 addresses typically results in higher transaction fees and less efficient block usage compared to modern SegWit addresses.
2. **Variable address lengths:** Due to the mathematical nature of the encoding base, resulting string lengths can fluctuate slightly, usually between 33 and 35 characters. This variability adds parsing complexity to automated scripts and accounting systems.

## Bech32 (BIP 173)

Bech32 is Bitcoin's native address format for SegWit outputs. It replaces the older Base58 format to offer stronger error detection and correction and improved human readability. Unlike Base58, it's built natively around powers of two and formal coding theory.

**5-bit groups, not 8-bit bytes:** Bech32 uses a 32-character alphabet (`qpzry9x8gf2tvdw0s3jn54khce6mua7l`), meaning each character encodes exactly 5 bits. Since 32 = 2⁵, so converting binary data to Bech32 is just bit-regrouping, no multi-precision division required. This is what collapses the O(n²) Base58 conversion cost down to a simple, linear O(n) bit-shifting operation.

**Single case, deliberately restricted alphabet, and the HRP (Human-Readable Part):** The Bech32 alphabet consists of lowercase characters only, and it deliberately excludes visually similar characters (`1`, `i`, `b`, `o`) to reduce human transcription errors before the checksum even gets involved. Every Bech32 string starts with a prefix identifying context, `bc` for Bitcoin mainnet, `tb` for testnet, and `bcrt` for Bitcoin regtest, separated from the payload by the numeral `1`. This is why native SegWit addresses start with `bc1`, `tb1`, or `bcrt1`.

**BCH-code checksum:** The final 6 characters of any Bech32 address aren't part of the payload, they're a checksum generated by a polynomial construction over a Galois field with 32 elements, matching the 5-bit alphabet. Bech32's checksum is a **BCH code** (Bose-Chaudhuri-Hocquenghem), a class of algebraic error-correcting codes originally developed for communications and storage systems, adapted here for human-typed strings.

The BIP 173 checksum is specifically constructed to guarantee: 100% detection of any single substitution error (one character typo), 100% detection of any two substitution errors (2 character typo), and strong detection of longer burst errors

```Burst errors that are confined to run of up to 4 consecutive characters is guaranteed to be caught, and detection remains good, though not guranteed beyond that```

Bech32 as deployed in Bitcoin is used primarily for **detection**, not automatic correction, wallets simply reject an invalid checksum and ask the user to re-check the address, rather than silently guessing the closest valid one.

**Reference implementation** (checksum computation):

```python
def bech32_polymod(values):
    """Internal function that computes the Bech32 checksum."""
    generator = [0x3b6a57b2, 0x26508e6d, 0x1ea119fa, 0x3d4233dd, 0x2a1462b3]
    chk = 1
    for value in values:
        top = chk >> 25
        chk = (chk & 0x1ffffff) << 5 ^ value
        for i in range(5):
            chk ^= generator[i] if ((top >> i) & 1) else 0
    return chk
```

## Conclusion

SegWit and Bech32 solve two different problems that are easy to mix up. SegWit restructured what a transaction output looks like, separating witness data from the base transaction to fix malleability, enable the linear-time sighash, and unlock the block-weight discount while Bech32 restructured how that output gets written down, replacing Base58's ad hoc, its computationally awkward encoding, with a format grounded in formal coding theory, one that's cheaper to process, harder to misread, and mathematically guaranteed to catch the most common classes of human error.
